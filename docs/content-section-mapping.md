# Content map: understanding, building, deepening, experimenting

**Status:** editorial classification baseline, 2026-10-30; implementation-evidence columns refreshed 2026-11-03 after the reference inference implementation (`src/llm_lab/foundations/`) landed, and the page inventory reconciled against the rendered sidebar and page-map tags on 2026-11-03. On 2026-11-03 the owner ratified the rule that advanced comprehension lives in the Deepen destination: the four advanced panorama readings (scaling-laws, emergence, in-context-learning, hybrid-llm-architectures) are reclassified from Understand to Deepen. The same day, inline advanced blocks were moved out of Understand lessons into existing Deepen pages: the soft-target/KL derivation from `cross-entropy` to `language-modeling-math`, and the embedding parameter-cost accounting from `embedding-space` to `tensors`.  
**Purpose:** make the reader-facing boundary between the conceptual course, the guided build, optional depth, and practice explicit. This is a source inventory, not a claim that every mapped implementation or experiment exists.

## 1. The four destinations have different jobs

| Destination | Main learner question | Owns | Does not own |
|---|---|---|---|
| **Understand** | What happens in an LLM, why does the mechanism exist, and how does it fit into the whole? | System explanations, LLM-specific definitions, intuitions, essential equations, small worked examples, assumptions and limitations | Full software implementations, broad prerequisite textbooks, long derivations unrelated to the LLM question |
| **Build** | How do I turn these ideas into a working small GPT? | Ordered implementation milestones, tested Python code (currently NumPy in the reference implementation), interfaces, tensor contracts, tests, checkpoints, reproducibility and implementation evidence | A second explanation of every concept; general mathematical courses |
| **Deepen** | Why does the mechanism have these properties, and where do the assumptions or limits come from? | Detailed derivations, mathematical foundations, shape algebra, alternative formulations, variants, research discussions and critical analyses | Mandatory prerequisites for the first conceptual overview or first implementation |
| **Practice & experiment** | Can I calculate, implement, test, vary or falsify something? | Exercises, hidden solutions, interactive explorations, unit/property tests as learning activities, experiment protocols and reports | Untethered demonstrations, decorative widgets, or claims that a toy experiment establishes production-scale behavior |

**Classification is based on the primary learning objective, not on the presence of equations or code.** A concept lesson may contain a small equation or short illustrative snippet and remain in Understand. A Build milestone may explain only the local mathematics needed to implement the next component. A Deepen page may include runnable code as evidence without becoming an implementation tutorial.

## 3. What belongs in the guided build

The Build route is a **sequence of implementation checkpoints**, not a parallel concept catalogue. It reuses the canonical pages above. Milestone IDs follow the authoritative inventory in [learning-path.md](learning-path.md): G2 is the parallel training-data branch; the inference branch runs G0–G1 → G3–G7.

| Build milestone | Conceptual source pages | Minimum practical learning | Current repository evidence |
|---|---|---|---|
| G0 — Define the target | LLM panorama, then Transformer overview and glossary; history as optional context only | State what a decoder-only GPT does and distinguish it from other model families | Bilingual panorama published on `main`; embedded checks cover architecture/objective and RAG/fine-tuning distinctions. Browser review and #108 acceptance remain pending. Historical reading is not a prerequisite |
| G1 — Prepare text and tokenizer | Text/data, Unicode, tokenization | Load a licensed corpus, tokenize/decode, document provenance and deterministic splits | Conceptual pages include self-checks for token-ID semantics and tokenizer-specific ID spaces; no complete end-to-end corpus/tokenizer pipeline is established by this audit |
| G2 — Create training examples | Training examples | Build context windows, shifted targets, batches and masks; test alignment and leakage boundaries | Detailed conceptual explanation exists; a minimal sliding-window input/target construction is implemented and tested (`training_examples.py`, `test_training_examples.py`); a production-ready corpus/batching pipeline is not established |
| G3 — Represent tokens | Embedding space, positional encoding; tensors as needed | Use embedding lookup and positional information; inspect only the shapes required by the implementation | Token and learned absolute position embeddings are implemented and tested inside the reference GPT (`gpt.py`, `test_gpt.py`); a standalone embedding module is not established. Bilingual formative lookup/shape practice is drafted under #220 but not yet integrated into learner-facing pages; browser review is deferred to #320 |
| G4 — Implement attention | Q/K/V, scaled attention, causal masking | Implement and test causal self-attention; verify shape and no-future-information invariants | Single-head attention primitives (`scaled_dot_product_attention`, `causal_mask`, `softmax_with_temperature`) are implemented and tested in `attention.py` (`test_attention.py`); multi-head attention is assembled and tested inside `transformer_block.py`; a standalone multi-head attention module is not established |
| G5 — Assemble a GPT block/model | Transformer overview; tensor reference as needed | Compose attention, residual paths, normalization, MLP and output projection into a configured model | A configurable, tested decoder-only GPT exists in `src/llm_lab/foundations/` (`gpt_config.py`, `gpt_ops.py`, `transformer_block.py`, `gpt.py`; one test file per module); NumPy, inference only |
| G6 — Predict and select | Logits, probabilities | Obtain vocabulary logits, read the conditional distribution, apply greedy or sampled selection; decoding never changes parameters | Greedy selection and temperature sampling are implemented and tested in `generate.py` (`test_generate.py`); top-k/top-p variants are not |
| G7 — Generate with fixed parameters | Transformer, logits, probabilities | Run the autoregressive loop with a sliding context window; expect incoherent output from untrained parameters | The decoding loop is implemented and tested (`generate.py`, `test_generate.py`); no KV cache and no early stopping (documented limitations); checkpoint-based generation awaits training |
| G8 — Train and validate | Training examples, cross-entropy, loss, gradients, experimental evaluation | Align logits/targets, compute the loss, backpropagate, update parameters, validate and checkpoint | Isolated loss/gradient helpers exist (`losses.py`, `test_losses.py`); no training loop or end-to-end run is established |
| G9 / E1 — Verify and evaluate | Experimental evaluation and relevant concept pages | Compare against a reference only under compatible conditions; analyze baselines, metrics, errors and limits | Evaluation-method content exists; no complete evaluation of a trained GPT is established |

A milestone may use a short local explanation of a tensor operation, derivative, or probability calculation. That does **not** make a full mathematics course a prerequisite. The implementation should teach the smallest useful operation at the point of use, with a link to Deepen for readers who want the derivation.

## 5. Prerequisite policy: minimum viable knowledge, then optional depth

Use three explicit levels:

1. **Must know now:** a small fact or operation without which the next step cannot be performed or interpreted safely.
2. **Learn in context:** the local explanation supplied immediately before or during the relevant build step.
3. **Optional depth:** a derivation, generalization, proof, variant, or advanced treatment that is not required to complete the first small GPT.

Examples:

- Before using `nn.Embedding`, the learner needs to know that token IDs index a learned lookup table and what input/output shapes mean. They do not need a course in vector spaces.
- Before using attention, the learner needs to understand the roles of Q/K/V, softmax over the key positions, and the causal constraint. They do not need to derive every property of matrix multiplication.
- Before calling `loss.backward()`, the learner needs to understand that the loss is a scalar objective and gradients indicate local sensitivity. They do not need a full course in multivariable calculus.
- Before sampling, the learner needs to understand that logits define a categorical distribution and that decoding transforms or samples from it. They do not need general information theory.

Never label a concept as a mandatory prerequisite merely because it is mathematically related. State the specific operation or claim that requires it.

## 6. Editorial rules for page changes

- **Do not split by subject name alone.** “Attention” can have a conceptual lesson, a tested implementation checkpoint, and a mathematical deep dive because these answer different questions.
- **Do not duplicate canonical explanations.** Build pages link to Understand; Deepen links back to the applied concept; exercises link to both.
- **Do not hide essential mathematics.** A public LLM lesson must remain independently understandable without private repositories. Keep the definitions and derivations needed for its stated learning objective.
- **Do not front-load prerequisites.** Introduce tensor operations, probability and gradients when the learner encounters them.
- **Do not overstate implementation status.** A code snippet is illustrative unless it is part of the maintained package and covered by relevant tests. A test suite does not establish model quality.
- **Do not advertise absent practical content.** Build milestones must carry explicit status until code, tests and evidence exist.
- **Keep advanced comprehension inside Deepen.** Any material whose primary learning objective requires advanced understanding belongs to the Deepen destination (Approfondir / Deepen your understanding) — in an existing page or a new one — and carries `destination:deepen`; a page tagged `level:advanced` must not claim `destination:understand`. (Owner decision, 2026-11-03.)
- **Keep bilingual parity.** Every reader-facing route and major lesson must have equivalent FR/EN learning objectives, caveats, status and links.
